المحور الأول: أنواع التحويل في الجافا بالتفصيل (Multiple Types of Casting)

التحويل (Casting) في لغة الجافا هو عملية تغيير نوع البيانات من نوع إلى آخر، وينقسم في الجافا إلى عائلتين مختلفتين تماماً في طريقة العمل والقواعد: تحويل الأنواع البدائية (Primitive Casting) وتحويل الكائنات والمراجع (Reference / Object Casting).

أولاً: تحويل الأنواع البدائية (Primitive Type Casting)

يتعامل هذا النوع مع القيم الرقمية والحرفية البسيطة (مثل int و double و long و byte)، وينقسم إلى نوعين:

  • التحويل التلقائي أو التوسيع (Widening / Implicit Casting):
    يحدث عندما تنقل قيمة من نوع صغير المساحة في الذاكرة إلى نوع أكبر مساحة (من الصغير إلى الكبير: byte ثم short ثم int ثم long ثم float ثم double).
    • لماذا هو تلقائي؟ لأنه آمن بنسبة مئة بالمئة ولا يوجد أي احتمال لفقدان جزء من الرقم، لذلك يقوم به المترجم (Compiler) تلقائياً دون تدخل منك.
  • التحويل اليدوي أو التضييق (Narrowing / Explicit Casting):
    يحدث عندما تحاول وضع قيمة كبيرة المساحة داخل متغير أصغر مساحة (من الكبير إلى الصغير، مثل تحويل double إلى int).
    • لماذا هو يدوي؟ لأن هناك احتمالاً لفقدان البيانات (مثل ضياع الكسور العشرية أو تجاوز الحد الأقصى للمتغير Overflow)، فيجبرك المترجم على كتابة النوع بين قوسين لتتحمل المسؤولية.

Java

// التوسيع التلقائي (من صغير لكبير - آمن)
int smallNumber = 50;
double bigNumber = smallNumber; // النتيجة: 50.0 (تلقائي)

// التضييق اليدوي (من كبير لصغير - قد يفقد بيانات)
double price = 99.95;
int roundedPrice = (int) price; // النتيجة: 99 (ضاع الجزء العشري .95)

ثانياً: تحويل الكائنات والمراجع (Reference / Object Casting)

هذا النوع لا يغيّر الكائن الحقيقي الموجود في الذاكرة (Heap) إطلاقاً، بل يغيّر فقط "زاوية النظر" أو نوع المؤشر (Reference) الذي نمسك به هذا الكائن، ويعتمد كلياً على علاقة الوراثة (IS-A Relationship).

  • التحويل للأعلى (Upcasting):
    هو إسناد كائن من نوع الابن (Child) إلى متغير مرجعي من نوع الأب (Parent) أو الواجهة (Interface).
    • حكمه: يحدث تلقائياً (Implicit) بدون أقواس تحويل؛ لأن كل ابن هو بالضرورة نوع من أبيه (كل كلب Dog هو حيوان Animal).
    • فائدته: هو أساس تعدد الأشكال (Polymorphism)؛ إذ يتيح لك كتابة دوال تستقبل Animal أو List وتتعامل مع أي ابن يمرر لها بمرونة عالية.
  • التحويل للأسفل (Downcasting):
    هو إرجاع المؤشر من نوع الأب (Parent) إلى نوع الابن (Child) لكي تتمكن من الوصول إلى الدوال الخاصة بالابن فقط.
    • حكمه: يجب كتابته يدوياً بين قوسين (Child)؛ لأن المترجم لا يضمن أن الأب يحمل هذا الابن تحديداً.
    • خطورته: إذا كان الكائن الفعلي في الذاكرة من نوع Cat وأنت حاولت تحويل المؤشر Animal إلى (Dog)، سيمر الكود من المترجم دون خطأ، لكنه سينهار أثناء التشغيل (Runtime) ويرمي خطأ ClassCastException.

Java

class Animal{
    public void eat(){ System.out.println("Animal eats"); }
}

class Dog extends Animal{
    public void bark(){ System.out.println("Dog barks"); }
}

class Cat extends Animal{
    public void meow(){ System.out.println("Cat meows"); }
}

public class CastingDemo{
    public static void main(String[] args){
        // أولاً: Upcasting (تلقائي من ابن لأب)
        Animal myAnimal = new Dog();
        myAnimal.eat(); // يعمل بنجاح

        // ثانياً: Downcasting آمن (يدوي من أب لابن)
        Dog myDog = (Dog) myAnimal;
        myDog.bark(); // الآن نستطيع استدعاء دوال Dog الخاصة

        // ثالثاً: Downcasting قاتل (يرمي ClassCastException أثناء التشغيل)
        Animal anotherAnimal = new Cat();
        Dog wrongDog = (Dog) anotherAnimal; // انهيار! القطة ليست كلباً
    }
}

ثالثاً: الحماية قبل التحويل المعاكس (instanceof و Pattern Matching)

لتجنب انهيار السيرفر بسبب ClassCastException عند عمل Downcasting، يجب دائماً فحص نوع الكائن الحقيقي في الذاكرة باستخدام الكلمة المفتاحية instanceof. وفي إصدارات الجافا الحديثة (منذ إصدار جافا السادس عشر)، أُضيفت ميزة مطابقة الأنماط (Pattern Matching for instanceof) التي تفحص النوع وتقوم بالتحويل في خطوة واحدة نظيفة:

Java

// الطريقة القديمة
if (myAnimal instanceof Dog) {
    Dog d = (Dog) myAnimal;
    d.bark();
}

// الطريقة الحديثة الاحترافية (Pattern Matching)
if (myAnimal instanceof Dog d) {
    d.bark(); // المتغير d جاهز ومحول تلقائياً داخل هذا النطاق
}
  • ملاحظة حول التعميمات (Generics): كما درسنا سابقاً، التعميمات تمنعك من عمل Casting غير آمن بين القوائم؛ فلا يمكنك تحويل List<Dog> إلى List<Animal>، وإذا حاولت إجبار المترجم عبر Raw Types ستتلقى تحذير Unchecked Cast لأن المترجم لا يستطيع التحقق من النوع بعد محو الأنواع (Type Erasure).

المحور الثاني: فهم throws بعد اسم الدالة من الصفر حتى الاحتراف

لفهم معنى throws التي تأتي بعد اسم الدالة، وتشريح توقيع دالة orElseThrow المعقد، يجب أن نبني الفكرة خطوة بخطوة من الأساس.

أولاً: ما الفرق الجوهري بين throw و throws؟

يخلط الكثيرون بين الكلمتين لتشابه الحروف، لكن وظيفة كل واحدة مختلفة تماماً:

  • الكلمة throw (بدون حرف s): تُكتب داخل جسم الدالة (Method Body)، وهي فعل أمر يعني: "أوقف التنفيذ الآن وارمِ هذا الكائن من الخطأ فوراً" (تُتبع بكائن خطأ واحد مثل throw new RuntimeException()).
  • الكلمة throws (مع حرف s): تُكتب في رأس الدالة بعد الأقواس وقبل القوس المتعرج {، وهي مجرد "لافتة تحذير" أو إعلان في عقد الدالة تقول لمن سيستدعي هذه الدالة: "انتبه! هذه الدالة لا تعالج الأخطاء بداخلها؛ إذا حدث خطأ من النوع الفلاني أثناء عملها، فستقذفه في وجهك أنت وعليك أن تتصرف معه!".

ثانياً: شجرة الاستثناءات ولماذا أُجبرنا على استخدام throws؟

في لغة الجافا، كل الأخطاء ترث من الجد الأكبر Throwable، وتنقسم إلى عائلتين رئيسيتين تحددان متى تكون throws إجبارية ومتى تكون اختيارية:

  • الأخطاء غير المفحوصة (Unchecked Exceptions):
    هي كل كلاس يرث من RuntimeException (مثل NullPointerException، IllegalArgumentException، و ResourceNotFoundException التي نصنعها في Spring Boot).
    • حكمها مع throws: اختيارية تماماً. المترجم لا يجبرك على كتابة try-catch ولا كتابة throws في رأس الدالة؛ لأن هذه الأخطاء غالباً تنتج عن أخطاء منطقية في الكود وتنتشر للأعلى تلقائياً حتى يمسكها @RestControllerAdvice في Spring Boot.
  • الأخطاء المفحوصة (Checked Exceptions):
    هي كل كلاس يرث من Exception مباشرة دون المرور بـ RuntimeException (مثل IOException عند قراءة ملف، أو SQLException عند الاتصال بقاعدة بيانات).
    • حكمها مع throws: إجبارية بقوة القانون! تفرض الجافا هنا قاعدة تُسمى "امسك أو أعلن" (Catch or Specify). إذا كتبت سطر كود قد يرمي IOException، فالمترجم يرفض ترجمة البرنامج ويضع خطاً أحمر ما لم تقم بأحد أمرين:
      • الحل الأول (Catch): تغلف الكود بـ try { ... } catch (IOException e) { ... } وتعالج المشكلة داخل دالتك.
      • الحل الثاني (Specify): تتنصل من المسؤولية وترمي الكرة في ملعب من استدعاك، وذلك بكتابة throws IOException بعد اسم دالتك مباشرة!

Java

// مثال يوضح إجبارية throws مع Checked Exceptions
public class FileReaderService{

    // الدالة الأولى أعلنت باستخدام throws أنها قد ترمي IOException ولم تعالجه
    public void readFile(String path) throws IOException{
        Files.readString(Path.of(path)); // هذا السطر قد يرمي IOException
    }

    // الدالة الثانية استدعت الأولى، فأصبحت هي أيضاً مجبرة على المعالجة أو التمرير بـ throws
    public void processUserFile() throws IOException{
        readFile("data.txt");
    }
}

ثالثاً: تشريح توقيع دالة orElseThrow سطراً بسطر (سحر التعميم مع الاستثناءات)

الآن انظر إلى السطر الذي أرسلته من كلاس Optional في مكتبة الجافا القياسية، وسنفكك كل رمز فيه:

Java

public <X extends Throwable> T orElseThrow(Supplier<? extends X> exceptionSupplier) throws X

لماذا كتب مهندسو الجافا هذا التوقيع بهذا الشكل العبقري؟ لنتتبع أجزاءه الأربعة:

  • الجزء الأول <X Throwable extends>:
    هنا تُعرّف الدالة معامل نوع معمم جديد اسمه X، وتقيده بشرط أن يكون X من عائلة Throwable (أي أي نوع استثناء في الجافا، سواء كان Checked أو Unchecked).
  • الجزء الثاني T (نوع الإرجاع):
    إذا كان صندوق Optional ممتلئاً، فستُخرج الدالة القيمة الحقيقية من نوع T وتُرجعها لك.
  • الجزء الثالث (Supplier<? extends X> exceptionSupplier):
    تستقبل الدالة دالة Lambda (من نوع Supplier) وظيفتها إنشاء وإرجاع كائن الخطأ من نوع X (أو أي ابن يرث من X) فقط إذا كان الصندوق فارغاً.
  • الجزء الرابع throws X (بعد اسم الدالة):
    هنا تكمن العبقرية المسماة شفافية الاستثناءات (Exception Transparency)! الدالة تقول للمترجم: "أنا سأرمي نفس نوع الخطأ X الذي سيعطيني إياه المبرمج داخل الـ Supplier!".

انظر كيف يتصرف المترجم بناءً على نوع الاستثناء الذي تمرره أنت في الـ Lambda:

  • الحالة الأولى (تمرير Unchecked Exception — وهو الشائع في Spring Boot):
    عندما تكتب:userRepo.findById(id).orElseThrow(() -> new UserNotFoundException("Not found"));
    بما أن UserNotFoundException يرث من RuntimeException، يستنتج المترجم تلقائياً أن X = UserNotFoundException (وهو Unchecked). وبما أن throws X أصبحت تعني throws UserNotFoundException، فإن المترجم لا يجبرك على كتابة try-catch ولا throws في دالتك!
  • الحالة الثانية (تمرير Checked Exception):
    لو كتبت:userRepo.findById(id).orElseThrow(() -> new IOException("File error"));
    هنا يستنتج المترجم تلقائياً أن X = IOException (وهو Checked). فتتحول throws X في توقيع orElseThrow إلى throws IOException، فيجبرك المترجم فوراً على وضع try-catch أو إضافة throws IOException لدالتك!

بهذا التصميم المعمم الواحد، استطاعت دالة orElseThrow خدمة نوعي الاستثناءات في الجافا دون الحاجة لكتابة دالتين منفصلتين.

المحور الثالث: الدوال الجاهزة التي يستطيع الابن استخدامها في abstract class و interface

عندما يرث كلاس ابن (Child) من كلاس مجرد (abstract class) أو يطبق واجهة (interface)، ما هي الدوال المكتملة الجاهزة التي تصبح متاحة له؟

أولاً: في الكلاس المجرد (abstract class)

الكلاس المجرد هو كلاس حقيقي يمكنه احتواء دوال مكتملة (Concrete Methods) ودوال مجردة (abstract). يستطيع الابن استخدام الدوال الجاهزة التالية:

  • الدوال العادية المكتملة (public و protected): يرثها الابن كاملة ويستطيع استدعاءها مباشرة أو عمل Override لتعديلها.
  • الدوال المكتملة بدون محدد وصول (Package-Private): يرثها ويستخدمها الابن بشرط أن يكون الابن في نفس الحزمة (Package) الموجودة فيها دالة الأب.
  • الدوال النهائية (final): يرثها الابن ويستطيع استخدامها واستدعاءها كدالة جاهزة تماماً، لكن يُمنع عليه عمل Override لتغيير محتواها.
  • الدوال الثابتة (static): يمكن للابن استدعاءها باسمه أو باسم الأب، لكنها تتبع الكلاس ولا تخضع للوراثة الديناميكية (Overriding).
  • الممنوع على الابن: الدوال الخاصة (private) داخل الكلاس المجرد تبقى محصورة بداخله فقط، ولا يراها الابن ولا يستطيع استدعاءها.

ثانياً: في الواجهة (interface)

تطورت الواجهات في الجافا الحديثة (منذ إصدار جافا الثامن والتاسع) لتحتوي على دوال مكتملة الكود، وتنقسم إلى ثلاثة أنواع تحكم علاقة الابن بها:

  • الدوال الافتراضية (default methods — منذ جافا الثامن):
    هي النوع الوحيد من الدوال المكتملة في الـ interface الذي يرثه الابن ويستطيع استخدامه جاهزاً مباشرة وكأنه مكتوب بداخله، كما يحق للابن عمل Override له إذا أراد.
  • الدوال الثابتة (static methods — منذ جافا الثامن):
    هي دوال مساعدة تابعة للواجهة نفسها فقط؛ لا يرثها الابن ولا يستطيع استدعاءها عبر كائن الابن ولا عبر اسم كلاس الابن! الطريقة الوحيدة لاستدعاءها هي كتابة اسم الواجهة مباشرة: InterfaceName.staticMethod().
  • الدوال الخاصة (private و private static — منذ جافا التاسع):
    هي دوال مساعدة داخلية تُكتب لخدمة دوال الـ default أو الـ static داخل نفس الواجهة لتجنب تكرار الكود؛ لا يراها الابن مطلقاً ولا يستطيع استدعاءها.
نوع الدالة المكتملةفي الكلاس المجرد (abstract class)في الواجهة (interface)
دالة عادية (public / protected)يرثها الابن ويستخدمها ويعدلهاغير موجودة (تتحول لـ abstract تلقائياً)
دالة افتراضية (default)غير مسموحة (خاصة بالواجهات فقط)يرثها الابن ويستخدمها جاهزة ويستطيع تعديلها
دالة نهائية (final)يرثها الابن ويستخدمها (ممنوع تعديلها)غير مسموحة في الواجهات
دالة ثابتة (static)متاحة للابن عبر اسم الكلاسحصرية للواجهة فقط (لا يرثها الابن أبداً)
دالة خاصة (private)مخفية تماماً عن الابنمخفية تماماً عن الابن

المحور الرابع: ما هي الدوال التي نستطيع استدعاءها عبر كائن الابن (Child Object)؟

لتحديد الدوال التي يُسمح لك بكتابتها بعد النقطة obj.، تطبق الجافا قاعدة ذهبية تفصل بين وقت الكتابة (Compile-time) ووقت التشغيل (Runtime):

القاعدة الذهبية: المترجم (Compiler) ينظر دائماً إلى نوع المؤشر الموجود على اليسار (Reference Type) ليقرر ما هي الدوال المسموح باستدعاءها، بينما ينظر نظام التشغيل (JVM) إلى نوع الكائن الحقيقي الموجود على اليمين (Object Type) ليقرر أي نسخة من الكود سينفذها!

بناءً على هذه القاعدة، لدينا حالتان أساسيتان عند التعامل مع كائن الابن:

الحالة الأولى: المؤشر من نوع الابن (Child obj = new Child();)

هنا يرى المترجم كل ما يملكه الابن وكل ما ورثه من عائلته، لذلك تستطيع استدعاء أربع مجموعات من الدوال عبر obj:

  • كل دوال الابن الخاصة به: أي دالة جديدة عرّفها الابن داخل كلاسه (public أو protected أو package-private في نفس الحزمة).
  • كل دوال الأب الموروثة (abstract class أو Normal class): سواء كانت دوال عادية مكتملة، أو دوال final، أو دوال مجردة قام الابن بتنفيذها.
  • كل الدوال الافتراضية (default) والتجريدية المنفذة من الواجهات (Interfaces): التي يطبقها الابن (implements).
  • كل دوال الجد الأكبر (Object): مثل toString() و equals() و hashCode() و getClass()؛ لأن كل كلاس في الجافا يرث من Object ضمنياً.

ما الذي لا تستطيع استدعاءه عبر obj حتى في هذه الحالة؟

  • الدوال الخاصة (private) في الأب أو الواجهة.
  • الدوال الثابتة (static) المعرفة داخل الـ interface (لأنها لا تُورَّث للكلاس الابن).

الحالة الثانية: المؤشر من نوع الأب أو الواجهة (Parent obj = new Child(); — تعدد الأشكال)

هذه هي الحالة الأكثر استخداماً في Spring Boot (مثل List<String> list = new ArrayList<>() أو PaymentService service = new StripePaymentService()). هنا تتغير القواعد كالتالي:

  • المسموح استدعاؤه عبر obj: فقط الدوال المُعلنة داخل كلاس الأب (Parent) أو الواجهة (Interface) (بالإضافة إلى دوال كلاس Object).
  • الممنوع استدعاؤه عبر obj: يُمنع عليك استدعاء أي دالة جديدة أضافها الابن Child من عنده ولم تكن موجودة في الأب! المترجم سيُظهر خطأ أحمر فوراً لأنه ينظر لنوع المؤشر Parent على اليسار ولا يرى فيه هذه الدالة. (للوصول إليها يجب عمل Downcasting أولاً كما شرحنا في المحور الأول).
  • أي نسخة تُنفَّذ عند التشغيل؟ إذا كانت الدالة موجودة في الأب وقام الابن بعمل Override لها، فسيتم تنفيذ نسخة الابن تلقائياً بفضل الربط الديناميكي (Dynamic Method Dispatch).

Java

interface Notifiable{
    void sendAlert(); // دالة مجردة

    default void logNotification(){ // دالة جاهزة يرثها الابن
        System.out.println("Logging notification...");
    }

    static void printSystemInfo(){ // دالة ثابتة حصرية للواجهة
        System.out.println("Notification System v1");
    }
}

abstract class BaseUser{
    public void login(){ // دالة جاهزة في الكلاس المجرد
        System.out.println("User logged in");
    }

    public abstract void accessDashboard(); // دالة مجردة
}

class AdminUser extends BaseUser implements Notifiable{
    @Override
    public void accessDashboard(){
        System.out.println("Admin Dashboard opened");
    }

    @Override
    public void sendAlert(){
        System.out.println("Admin Alert sent!");
    }

    // دالة خاصة بالابن فقط
    public void deleteDatabase(){
        System.out.println("Database deleted!");
    }
}

public class ObjectMethodsDemo{
    public static void main(String[] args){
        // الحالة الأولى: المؤشر من نوع الابن (كل شيء متاح)
        AdminUser admin = new AdminUser();
        admin.login();             // جاهزة من BaseUser
        admin.accessDashboard();   // منفذة في AdminUser
        admin.logNotification();   // جاهزة (default) من Notifiable
