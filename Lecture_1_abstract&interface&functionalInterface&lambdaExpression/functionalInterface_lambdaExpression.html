ال Functional Interface (الواجهة الوظيفية) هي أي واجهة (interface) في لغة جافا تحتوي على دالة مجردة واحدة فقط (Single Abstract Method - SAM)، وتمثل الجسر الذي سمح للجافا بالانتقال من البرمجة كائنية التوجه الصارمة (OOP) إلى البرمجة الوظيفية (Functional Programming) ابتداءً من إصدار Java 8.

لفهمها وتدريسها للطلاب بسهولة، تخيل أننا قبل Java 8 كنا نمرر للدوال "بيانات فقط" (مثل رقم int أو نص String أو كائن User). لكن أحياناً نحتاج أن نمرر للدالة "سلوكاً أو فعلاً" (Behavior) — أي نمرر لها "كوداً لتنفذه" مثلما نمرر لها متغيراً. ولأن الجافا لا تسمح بوجود دوال حرة خارج الكلاسات، ابتكر مهندسو الجافا الـ Functional Interface لتكون "الحاوية" التي تغلف هذا السلوك وتنقله من مكان لآخر.

1. القاعدة الذهبية لتعريف الـ Functional Interface (قاعدة SAM)

لكي يُعتبر أي interface واجهة وظيفية صالحة، يجب أن يلتزم بقانون SAM (Single Abstract Method):

  1. دالة مجردة واحدة فقط: يجب أن يمتلك دالة واحدة فقط بدون جسم (بدون {})، وهي التي تحدد "شكل العقد" (المدخلات والمخرجات).
  1. يُسمح بوجود دوال default و static بأي عدد: وجود دوال مكتملة التنفيذ بداخل الواجهة لا يكسر القاعدة لأنها ليست مجردة.
  1. يُسمح بإعادة تعريف دوال كلاس Object: إذا كتبت دالة مثل boolean equals(Object o) أو String toString() داخل الواجهة، فإن المترجم (Compiler) لا يحسبها كدالة مجردة ثانية لأن كل كائن في جافا يرثها تلقائياً من Object.

دور التعليق التوضيحي @FunctionalInterface

وضع @FunctionalInterface فوق الواجهة اختياري من ناحية التشغيل، لكنه إجباري هندسياً كصمام أمان (مثل @Override). إذا وضعته ثم أتى زميلك في الفريق وأضاف دالة مجردة ثانية عن طريق الخطأ، سيمنعه المترجم فوراً ويظهر خطأ (Compile-time Error) قبل أن تتعطل أكواد الـ Lambda المعتمدة على هذه الواجهة.

Java

@FunctionalInterface
public interface DiscountRule{
    // 1. الدالة المجردة الوحيدة (SAM)
    double applyDiscount(double price);

    // 2. مسموح بدوال default
    default void printInfo(){
        System.out.println("Applying discount rule...");
    }

    // 3. مسموح بدوال static
    static boolean isValidPrice(double price){
        return price > 0;
    }
}

2. رحلة التطور: من الكود التقليدي إلى الاحتراف (4 مراحل)

عند شرح هذا الموضوع للطلاب، أفضل طريقة لترسيخ الفكرة هي عرض نفس المثال بأربع طرق متدرجة من الأقدم للأحدث:

المرحلة الأولى: الكلاس التقليدي (ما قبل Java 8)

ننشئ كلاساً منفصلاً يطبق الواجهة، ثم ننشئ منه كائناً:

Java

class VipDiscount implements DiscountRule{
    @Override
    public double applyDiscount(double price){
        return price * 0.80; // خصم 20%
    }
}
// الاستخدام:
DiscountRule rule = new VipDiscount();

المرحلة الثانية: الكلاس الداخلي المجهول (Anonymous Inner Class)

لتجنب إنشاء ملفات كثيرة، كنا نكتب التنفيذ مباشرة، لكن الكود كان مليئاً بالحشو (Boilerplate):

Java

DiscountRule rule = new DiscountRule() {
    @Override
    public double applyDiscount(double price){
        return price * 0.80;
    }
};

المرحلة الثالثة: تعبير اللامدا (Lambda Expression - Java 8)

بما أن الواجهة لا تملك إلا دالة واحدة، فالمترجم يعرف اسمها ونوع مدخلاتها ومخرجاتها مسبقاً! لذا نحذف اسم الكلاس، واسم الدالة، وأنواع المتغيرات، ونبقي فقط على (المدخلات) -> (التنفيذ):

Java

// الصيغة الكاملة:
DiscountRule rule1 = (double price) -> {
    return price * 0.80;
};

// الصيغة المختصرة الاحترافية:
DiscountRule rule2 = price -> price * 0.80;

قواعد اختصار الـ Lambda (للحفظ والفهم):

  • إذا كان هناك مدخل واحد فقط، يمكنك حذف الأقواس () حوله (أما لو صفر مدخلات () أو مدخلان (a, b) فالأقواس إجبارية).
  • لا داعي لكتابة نوع المدخل (double) لأن المترجم يستنتجه من الواجهة (Type Inference).
  • إذا كان جسم الدالة سطراً واحداً فقط، احذف الأقواس المعقوفة {} واحذف كلمة return والفاصلة المنقوطة بداخلها.

المرحلة الرابعة: مراجع الدوال (Method References ::)

إذا كان الـ Lambda لا يفعل شيئاً سوى استدعاء دالة جاهزة وموجودة مسبقاً، نختصره أكثر باستخدام نقطتين رأسيتين ::، ولها 4 أنواع فقط:

النوعالصيغةمثال Lambdaالمكافئ بـ Method Reference
1. دالة ثابتة (Static Method)ClassName::staticMethodx -> Integer.parseInt(x)Integer::parseInt
2. دالة لكائن محدد (Specific Object)objectInstance::methodmsg -> System.out.println(msg)System.out::println
3. دالة لكائن عام من نفس النوع (Arbitrary Object)ClassName::instanceMethodstr -> str.toLowerCase()String::toLowerCase
4. المُنشئ (Constructor)ClassName::newname -> new User(name)User::new

3. الأبطال الأربعة في حزمة java.util.function

بدلاً من أن يكتب كل مبرمج واجهة جديدة في كل مشروع، وفرت جافا حزمة جاهزة تسمى java.util.function تحتوي على أكثر من 40 واجهة، كلها مبنية على 4 واجهات أساسية فقط. إذا أتقنت هذه الأربع، فقد أتقنت 80% من البرمجة الوظيفية في جافا، وStreams، وOptional، وSpring:

1. Predicate<T> (المُختبِر / الفلتر)

  • وظيفتها: تأخذ قيمة من نوع T وتفحص شرطاً معيناً عليها، ثم ترجع boolean (true أو false).
  • دالتها المجردة: boolean test(T t)
  • أين تراها؟ في دالة .filter() داخل Stream و Optional.
  • مثال عملي:

Java

Predicate<String> isStrongPassword = pass -> pass.length() >= 12 && pass.contains("@");
System.out.println(isStrongPassword.test("Admin@123456")); // true

2. Function<T, R> (المُحوّل / المصنع)

  • وظيفتها: تأخذ مدخلاً من نوع T، تجري عليه معالجة أو تحويلاً، وترجع مخرجاً من نوع R (قد يكون نفس النوع أو نوعاً مختلفاً تماماً).
  • دالتها المجردة: R apply(T t)
  • أين تراها؟ في دالة .map() لتحويل كائن User إلى UserDTO في مشاريع Spring Boot.
  • مثال عملي:

Java

Function<String, Integer> getTextLength = text -> text.length();
System.out.println(getTextLength.apply("Spring Security")); // 15

3. Consumer<T> (المُستهلك / المُنفّذ)

  • وظيفتها: تأخذ قيمة من نوع T وتنفذ عليها إجراءً جانبياً (مثل الطباعة، الحفظ في قاعدة البيانات، إرسال إيميل)، ولا ترجع شيئاً (void).
  • دالتها المجردة: void accept(T t)
  • أين تراها؟ في دالة .forEach() ودالة .ifPresent().
  • مثال عملي:

Java

Consumer<String> logSecurityAlert = alert -> System.err.println("[ALERT]: " + alert);
logSecurityAlert.accept("Multiple failed login attempts!");

4. Supplier<T> (المُورّد / المولّد)

  • وظيفتها: لا تأخذ أي مدخلات ()، ولكنها تُنتج لك وتُرجع قيمة من نوع T عند الطلب (Lazy Generation).
  • دالتها المجردة: T get()
  • أين تراها؟ في دالة .orElseGet() في Optional، أو توليد أرقام عشوائية ورموز OTP.
  • مثال عملي:

Java

Supplier<String> generateOtp = () -> String.valueOf((int) (Math.random() * 9000) + 1000);
System.out.println(generateOtp.get()); // مثلاً: 4829

4. التوسعات المتقدمة في java.util.function (الوصول للاحتراف)

بمجرد أن يفهم الطالب الأبطال الأربعة، سيستوعب باقي الحزمة تلقائياً لأنها مجرد تنويعات منطقية عليها:

أ. النسخ ثنائية المدخلات (Bi-Variants)

عندما تحتاج دالتك إلى مدخلين بدلاً من مدخل واحد، أضف كلمة Bi في البداية:

  • BiPredicate<T, U>: يأخذ مدخلين ويرجع boolean — دالتها: boolean test(T t, U u)
    • مثال: التحقق من تطابق اسم المستخدم وكلمة المرور: (user, pass) -> checkAuth(user, pass)
  • BiFunction<T, U, R>: يأخذ مدخلين (T, U) ويرجع نتيجة (R) — دالتها: R apply(T t, U u)
    • مثال: حساب السعر النهائي بناءً على السعر الأساسي ونسبة الضريبة: (price, tax) -> price + (price * tax)
  • BiConsumer<T, U>: يأخذ مدخلين ولا يرجع شيئاً (void) — دالتها: void accept(T t, U u)
    • مثال: المرور على عناصر HashMap باستخدام map.forEach((key, value) -> ...)

ب. العوامل الموحدة (Operators)

هي حالات خاصة من Function و BiFunction عندما يكون نوع المدخلات هو نفسه تماماً نوع المخرجات:

  • UnaryOperator<T>: يرث من Function<T, T>. يأخذ T ويرجع T.
    • مثال: تنظيف النصوص: UnaryOperator<String> clean = s -> s.trim().toUpperCase();
  • BinaryOperator<T>: يرث من BiFunction<T, T, T>. يأخذ اثنين من نوع T ويرجع واحداً من نفس النوع T.
    • مثال: جمع رقمين أو اختيار الأكبر بينهما: BinaryOperator<Integer> max = (a, b) -> a > b ? a : b;

ج. النسخ المخصصة للأنواع البدائية (Primitive Specializations) — سر الأداء العالي!

في الجافا، الواجهات العامة مثل Predicate<Integer> لا تقبل الأنواع البدائية (int, long, double) بل تتطلب كائنات (Wrapper Classes). تحويل int إلى Integer وملايين المرات في السيرفر يُسمى Autoboxing / Unboxing ويستهلك الذاكرة (RAM) ويبطئ المعالج.

لذلك وفرت جافا نسخاً مخصصة تتعامل مع int و long و double مباشرة بدون تغليف:

  • IntPredicate, LongPredicate, DoublePredicate (تأخذ int مباشرة وترجع boolean).
  • IntConsumer, LongConsumer, DoubleConsumer (تأخذ int مباشرة وتنفذ أمراً).
  • IntSupplier, LongSupplier, DoubleSupplier, BooleanSupplier (ترجع int أو boolean بدائي مباشرة).
  • IntFunction<R>: تأخذ int بدائي وترجع كائن R.
  • ToIntFunction<T>: تأخذ كائن T وترجع int بدائي (ممتازة لحساب المجاميع والمتوسطات بسرعة فائقة).

5. تركيب الدوال (Function Composition) — ربط الدوال كقطع الليغو

الاحتراف الحقيقي يظهر عندما تدمج عدة دوال صغيرة لتبني منطقاً معقداً ومقروءاً باستخدام دوال default المدمجة داخل الواجهات الوظيفية:

1. دمج الشروط في Predicate (and, or, negate)

Java

Predicate<User> isActive = User::isActive;
Predicate<User> isAdmin = user -> user.getRole().equals("ADMIN");
Predicate<User> isBanned = User::isBanned;

// مستخدم نشط، وليس محظوراً، وإما أن يكون أدمن أو لديه صلاحية خاصة
Predicate<User> canAccessDashboard = isActive.and(isBanned.negate()).and(isAdmin);

boolean allowed = canAccessDashboard.test(currentUser);

2. تسلسل التحويلات في Function (andThen مقابل compose)

هذا موضع سؤال مشهور جداً في المقابلات التقنية:

  • f1.andThen(f2): ينفذ f1 أولاً، ثم يأخذ نتيجتها ويمررها إلى f2 (من اليسار لليمين).
  • f1.compose(f2): ينفذ f2 أولاً، ثم يأخذ نتيجتها ويمررها إلى f1 (من اليمين لليسار - عكس الترتيب).

Java

Function<Integer, Integer> multiplyBy2 = x -> x * 2;
Function<Integer, Integer> add10 = x -> x + 10;

// 1. andThen: اضرب في 2 أولاً (3 * 2 = 6)، ثم اجمع 10 (6 + 10 = 16)
int res1 = multiplyBy2.andThen(add10).apply(3); // النتيجة: 16

// 2. compose: اجمع 10 أولاً (3 + 10 = 13)، ثم اضرب في 2 (13 * 2 = 26)
int res2 = multiplyBy2.compose(add10).apply(3); // النتيجة: 26

3. تسلسل الأوامر في Consumer (andThen)

Java

Consumer<String> saveToDb = data -> System.out.println("Saving to PostgreSQL: " + data);
Consumer<String> sendAuditLog = data -> System.out.println("Logging audit event: " + data);

// ينفذ الحفظ أولاً، ثم يسجل الحدث في اللوج تلقائياً
Consumer<String> processOrder = saveToDb.andThen(sendAuditLog);
processOrder.accept("Order #99");

6. أسرار المستوى المتقدم (الفخاخ البرمجية وقواعد المعماريين)

لإبهار الطلاب وتجنب أخطاء الإنتاج (Production Bugs)، احرص على توضيح هذه النقاط الأربع:

  1. قاعدة Effectively Final (لماذا يُمنع تعديل المتغيرات المحلية داخل Lambda؟):

    إذا عرّفت متغيراً محلياً داخل دالة (مثل int count = 0;) وحاولت تغييره داخل تعبير Lambda (count++)، سيرفض المترجم ذلك.

    • السبب المعماري: المتغير المحلي يعيش في ذاكرة Stack ويموت بمجرد انتهاء الدالة، بينما الـ Lambda قد يُرسل ليُنفذ في Thread آخر أو في وقت لاحق، لذا تأخذ الجافا نسخة (Copy) من قيمة المتغير. ولضمان عدم حدوث تضارب بين النسخة والأصل (Race Condition)، تشترط الجافا ألا تتغير قيمة هذا المتغير أبداً (إما final صراحةً أو Effectively Final أي لم يُعد تعيينه). (ملاحظة: يمكن تعديل متغيرات الكلاس Instance Variables لأنها تعيش في الـ Heap).
  1. الفرق في نطاق الكلمة المفتاحية this:
    • داخل Anonymous Inner Class: كلمة this تشير إلى الكلاس المجهول نفسه.
    • داخل Lambda Expression: الـ Lambda لا ينشئ نطاقاً (Scope) جديداً، لذا كلمة this تشير إلى الكلاس الخارجي الذي كُتبت بداخله الـ Lambda.
  1. فخ الاستثناءات المُجبرة (Checked Exceptions):

    الدوال القياسية في java.util.function (مثل Function.apply) لا تحتوي في توقيعها على throws Exception. لذلك، إذا استدعيت دالة ترمي Checked Exception (مثل IOException أو SQLException) داخل Lambda، سيعترض المترجم.

    • الحل الاحترافي: إما تغليف الاستدعاء بـ try-catch وتحويله إلى RuntimeException، أو إنشاء Functional Interface مخصص لك يدعم الاستثناءات (مثل @FunctionalInterface public interface ThrowingFunction<T, R, E extends Exception> { R apply(T t) throws E; }).
  1. متى تنشئ Functional Interface خاصاً بك بدلاً من الجاهز؟

    استخدم حزمة java.util.function في 95% من الحالات، ولا تنشئ واجهة مخصصة إلا في حالتين:

    • عندما تحتاج إلى 3 مدخلات أو أكثر (لأن جافا توفر مدخلين كحد أقصى BiFunction).
    • عندما يكون للواجهة معنى تجاري أو أمني واضح جداً (Domain Semantics) يزيد من مقروئية الكود، مثل واجهة Customizer<T> الشهيرة في Spring Security 6 التي ستراها في كل سطر تقريباً في كتاب Laurentiu Spilca (مثل http.cors(cors -> ...)).

هل ترغب في أن نصمم معاً تمارين تطبيقية متدرجة من السهل إلى الصعب (مع حلولها) لتعطيها للطلاب في نهاية شرحك، أم ننتقل لرؤية كيف يوظف Spring Security 6 هذه الواجهات عملياً؟
