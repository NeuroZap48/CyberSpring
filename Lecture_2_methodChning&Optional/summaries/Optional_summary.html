الفلسفة الأساسية: ما هو Optional ولماذا وُجد؟

يُعد كلاس Optional<T> حاوية تغليف (Wrapper Container) أُضيفت في إصدار جافا الثامن ضمن حزمة java.util، ويمكن تخيله كصندوق مغلف قد يحتوي بداخله على كائن حقيقي (Object) أو يكون فارغاً تماماً (empty).

تم ابتكار هذا المفهوم لحل أشهر مشكلة تسبب انهيار التطبيقات في وقت التشغيل (Runtime)، وهي خطأ NullPointerException — والذي وصفه مبتكر فكرة القيمة الفارغة (توني هور) بأنه خطأ المليار دولار.

لماذا لا نكتفي بجملة الشرط التقليدية؟

  • توثيق صريح في توقيع الدالة (Self-Documenting API): عندما ترى دالة مكتوبة بصيغة User findById(Long id)، فأنت لا تعرف هل ستعيد قيمة null عند عدم وجود المستخدم أم سترمي استثناءً، مما يضطرك لقراءة كود الدالة من الداخل. أما عندما ترى Optional<User> findById(Long id)، فتوقيع الدالة نفسه يخبرك صراحةً أن النتيجة قد تكون غير موجودة وعليك التعامل مع هذا الاحتمال.
  • تحويل الخطأ من وقت التشغيل إلى وقت الكتابة (Compile-time): مع المتغير العادي، إذا نسيت فحص القيمة وكتبت user.getName() مباشرة، سيسمح لك المترجم (Compiler) بالمرور وسينهار السيرفر لاحقاً عند العميل. أما مع Optional، فالمترجم يمنعك من الوصول للدوال الداخلية مباشرة ويُجبرك على فتح الصندوق أولاً واختيار سيناريو التعامل مع غياب القيمة.
  • دعم البرمجة الوظيفية (Functional Style): يتيح لك دمج العمليات المتتالية (Chaining) مثل التحويل والتصفية في سطر واحد نظيف بدلاً من تداخل جمل الشروط المتشعبة (Spaghetti Code).

المرحلة الأولى: إنشاء الصندوق

توجد ثلاث طرق لإنشاء كائن Optional، والخلط بينها يسبب أخطاء شائعة في المشاريع:

اسم الدالةمتى تستخدمها في الكود؟النتيجة عند تمرير قيمة فارغة
دالة Optional.of(value)عندما تكون متأكداً بنسبة مئة بالمئة أن القيمة ليست null.ينهار البرنامج فوراً ويرمي NullPointerException في نفس السطر.
دالة Optional.ofNullable(value)الطريقة الأكثر استخداماً وأماناً؛ عندما لا تضمن هل القيمة موجودة أم لا (مثل بيانات قاعدة البيانات).لا يحدث أي خطأ، ويُرجع تلقائياً صندوقاً فارغاً Optional.empty().
دالة Optional.empty()عندما تريد إرجاع صندوق فارغ بشكل صريح ومباشر (مثل عدم العثور على نتيجة بحث).لا تأخذ أي معاملات وتنشئ صندوقاً فارغاً.

Java

String name = "Mohanad";
String nullName = null;

Optional<String> opt1 = Optional.of(name);           // يعمل بنجاح
// Optional<String> opt2 = Optional.of(nullName);    // يرمي NullPointerException فوراً!
Optional<String> opt3 = Optional.ofNullable(nullName); // آمن تماماً، النتيجة: Optional.empty
Optional<String> opt4 = Optional.empty();            // صندوق فارغ صريح

المرحلة الثانية: استخراج القيمة والتعامل مع الصندوق

بعد استلام الصندوق، تنقسم أدوات التعامل معه إلى أدوات تقليدية خطيرة وأدوات احترافية نظيفة:

أولاً: الطريقة التقليدية غير المفضلة

  • فحص الامتلاء عبر isPresent() والفراغ عبر isEmpty(): دالتان تفحصان حالة الصندوق فقط (أُضيفت isEmpty() في إصدار جافا الحادي عشر)، واستخدامهما يعيدنا لنفس عقلية الشرط التقليدية.
  • استخراج القيمة بالقوة عبر get(): تُخرج القيمة من الصندوق مباشرة، لكن استدعاءها على صندوق فارغ يرمي خطأ NoSuchElementException. استخدامها بدون فحص مسبق يُعد خطأً برمجياً فادحاً (Anti-pattern) وينصح الخبراء بتجنبها تماماً.

Java

// أسلوب غير مفضل (لا يفرق شيئاً عن فحص الشرط التقليدي)
if (optUser.isPresent()) {
    User u = optUser.get();
    System.out.println(u.getName());
}

ثانياً: الطريقة الاحترافية للتنفيذ المشروط

  • التنفيذ عند الوجود عبر ifPresent(Consumer<T>): إذا كانت القيمة موجودة داخل الصندوق، تنفّذ الأمر عليها؛ وإن كان الصندوق فارغاً، تتجاهل الأمر بصمت دون أي خطأ.
  • التنفيذ أو البديل عبر ifPresentOrElse(Consumer<T>, Runnable): أُضيفت في إصدار جافا التاسع لتكون بديلاً نظيفاً لجملة الشرط الكاملة، حيث تنفذ الأمر الأول إن وُجدت القيمة، وتنفذ الثاني إن كان الصندوق فارغاً.

Java

// تنفيذ أمر فقط عند وجود القيمة
optUser.ifPresent(user -> System.out.println(user.getName()));

// تنفيذ أمر عند الوجود وأمر آخر عند الغياب
optUser.ifPresentOrElse(
    user -> System.out.println("Welcome " + user.getName()),
    () -> System.out.println("User not found!")
);

ثالثاً: الطريقة الاحترافية للاستخراج مع قيمة بديلة أو خطأ

  • إرجاع قيمة بديلة مباشرة عبر orElse(T other): تُرجع القيمة الموجودة إن وُجدت، وإلا تُرجع القيمة البديلة الجاهزة other.
  • توليد قيمة بديلة عند الحاجة عبر orElseGet(Supplier<? extends T> supplier): تُرجع القيمة إن وُجدت، وإلا تُنفذ دالة (Lambda) لتوليد القيمة البديلة.
  • رمي استثناء مخصص عبر orElseThrow(...): تُعد الأهم في تطبيقات السيرفر (Spring Boot)، حيث تُرجع القيمة إن وُجدت، وإلا ترمي استثناءً مخصصاً تختاره أنت.
  • البحث في صندوق بديل عبر or(Supplier<Optional<T>>): أُضيفت في إصدار جافا التاسع؛ تشبه orElseGet لكنها تُرجع صندوق Optional بديل كامل وليس مجرد قيمة، وهي ممتازة للبحث المتسلسل (Chain of Responsibility).

Java

// مثال رمي استثناء مخصص في Spring Boot
User user = userRepository.findById(id)
    .orElseThrow(() -> new ResourceNotFoundException("User not found with id: " + id));

// مثال البحث المتسلسل: ابحث في الكاش أولاً، فإن لم تجد ابحث في قاعدة البيانات
Optional<User> cachedOrDbUser = findInCache(id)
    .or(() -> findInDatabase(id));

المرحلة الثالثة: التحويل والتصفية بدون فتح الصندوق

تظهر القوة الحقيقية لكلاس Optional في إمكانية معالجة البيانات الموجودة داخل الصندوق وهو مغلق (بأسلوب مشابه لـ Java Streams). إذا كان الصندوق فارغاً، يتم تخطي كل هذه العمليات بأمان تام دون أي خطأ.

  • تصفية القيمة عبر filter(Predicate<T>): تفحص القيمة داخل الصندوق بناءً على شرط محدد؛ فإذا تحقق الشرط تُبقي الصندوق كما هو، وإذا فشل الشرط (أو كان الصندوق فارغاً أصلاً) تُفرّغ الصندوق وتُرجع Optional.empty().
  • تحويل القيمة عبر map(Function<T, R>): تأخذ القيمة الموجودة داخل الصندوق، وتطبق عليها دالة تحويل، ثم تضع النتيجة الجديدة داخل صندوق Optional جديد.
  • فك الصناديق المتداخلة عبر flatMap(Function<T, Optional<R>>): نحتاجها عندما تُرجع دالة التحويل نفسها Optional آخر (مثل أن يُرجع المستخدم Optional<Address>). استخدام map العادية هنا ينتج صندوقاً داخل صندوق (Optional<Optional<Address>>)، بينما تقوم flatMap بدمجهما وتسطيحهما في صندوق واحد مباشر (Optional<Address>).

Java

// مثال التصفية
Optional<User> activeAdultUser = userRepository.findById(id)
    .filter(user -> user.isActive())
    .filter(user -> user.getAge() >= 18);

// مثال التحويل المتسلسل
String email = userRepository.findById(id)
    .map(User::getEmail)
    .map(String::toUpperCase)
    .orElse("NO_EMAIL@DOMAIN.COM");

// مثال فك الصناديق المتداخلة
String city = userRepository.findById(id)
    .flatMap(User::getAddress)
    .map(Address::getCity)
    .orElse("Unknown City");

فخ الأداء القاتل: الفرق بين orElse و orElseGet

يُعد هذا الفرق من أهم النقاط التي تؤثر مباشرة على أداء السيرفر واستهلاك الموارد:

  • التقييم الفوري (Eager Evaluation) في orElse(method()): تقوم الجافا بتنفيذ الدالة الموجودة داخل الأقواس دائماً في كل الحالات، حتى لو كان الصندوق ممتلئاً ولن نحتاج للقيمة البديلة أصلاً.
  • التقييم الكسول (Lazy Evaluation) في orElseGet(() -> method()): لا تقوم الجافا بتنفيذ دالة الـ Lambda إلا إذا كان الصندوق فارغاً فعلاً.

Java

// الصندوق ممتلئ بالقيمة "Mohanad"
Optional<String> opt = Optional.of("Mohanad");

// كارثة أداء: سيتم تنفيذ الدالة وحفظ مستخدم في قاعدة البيانات رغم أن الصندوق ممتلئ!
String name1 = opt.orElse(createDefaultUserInDB());

// أسلوب احترافي: لن يتم استدعاء الدالة إطلاقاً لأن الصندوق ممتلئ
String name2 = opt.orElseGet(() -> createDefaultUserInDB());

القاعدة الذهبية هنا هي استخدام orElse فقط للقيم الثابتة الجاهزة في الذاكرة (مثل نص ثابت أو قيمة صفرية)، واستخدام orElseGet دائماً إذا كان البديل يتطلب استدعاء دالة، أو إنشاء كائن جديد، أو الاستعلام من قاعدة بيانات.

مواضع يجب فيها تجنب استخدام Optional

صُمم Optional ليكون قيمة مرجعة من الدوال (Return Type) فقط، واستخدامه في الأماكن التالية يُعد ممارسة برمجية سيئة (Bad Practice):

  • مدخلات الدوال (Method Parameters): كتابة دالة تستقبل Optional<String> تُجبر من يستدعيها على تغليف القيمة في كل مرة، والأسوأ أنه قد يمرر لك null بدلاً من Optional.empty() فتضطر لفحص الاثنين معاً. البديل الصحيح هو استخدام Method Overloading.
  • خصائص الكلاسات (Class Fields والـ Entities): كلاس Optional لا يطبق واجهة Serializable، مما يسبب مشاكل مع مكتبات قواعد البيانات (Hibernate و JPA) وعند تحويل الكائنات إلى JSON عبر Jackson، بالإضافة لاستهلاكه مساحة إضافية في الذاكرة (Heap). الحل الصحيح هو تعريف الحقل كمتغير عادي وجعل دالة الـ Getter هي التي تُرجع Optional.
  • المجموعات والقوائم (Collections والـ Arrays): لا تضع قائمة داخل Optional مثل Optional<List<Student>>؛ لأن القائمة الفارغة (Collections.emptyList() أو List.of()) هي بحد ذاتها حاوية فارغة وآمنة تماماً عند المرور عليها ولا تسبب أي أخطاء.

Java

// الطريقة الصحيحة لاستخدام Optional داخل الكلاسات
public class User{
    private String middleName; // حقل عادي وليس Optional

    public Optional<String> getMiddleName(){
        return Optional.ofNullable(this.middleName); // التغليف يتم هنا فقط
    }
}

تمرين عملي سريع لاختبار الفهم

لنفترض أن لديك كائناً من نوع Order قد يكون فارغاً، وبداخله كائن Customer قد يكون فارغاً، وبداخله رقم هاتف phone قد يكون فارغاً؛ يمكننا اختصار ثلاث جمل شرطية متداخلة في سطر واحد محصّن تماماً ضد الانهيار:

Java

String phone = Optional.ofNullable(order)
    .map(Order::getCustomer)
    .map(Customer::getPhone)
    .orElse("N/A");

القاعدة الذهبية الوحيدة لنجاح وضع عدة دوال وراء بعض (Method Chaining) هي: كل دالة يجب أن تُرجع كائناً (Object) يمتلك في كلاسه الدالة التي تليها مباشرة.

تفكيرك قريب جداً من الصواب، ودعنا نضبط القواعد التي ذكرتها لتصبح دقيقة 100% وتنطبق على أي كود جافا تقابله:

1. بخصوص مثالك الأول: "هل يجب أن تُرجع نفس القيمة أو نفس النوع؟"

ليس شرطاً أن تُرجع الدوال نفس القيمة ولا حتى نفس النوع! المهم فقط أن ما يخرج من يسار النقطة (.) يكون كائناً يملك الدالة الموجودة على يمين النقطة. ولذلك للسلسلة 3 أشكال مشهورة:

  • الشكل الأول: تُرجع نفس الكائن بالضبط (return this)
    وهذا ما رأيته في StudentBuilder و StringBuilder؛ كل دالة تعدل على الكائن ثم تُرجعه نفسه لتكمل عليه.Java
    // كل دالة تُرجع نفس كائن الـ StringBuilder
new StringBuilder().append("Hello").append(" World").reverse();
  • الشكل الثاني: تُرجع كائناً جديداً من نفس النوع
    مثل دوال النصوص (String)؛ كل دالة تصنع نصاً جديداً وتُرجعه:Java
    // " ali " (String) -> .trim() ترجع String جديد -> .toUpperCase() ترجع String جديد
String result = "  ali  ".trim().toUpperCase();
  • الشكل الثالث: كل دالة تُرجع نوعاً مختلفاً تماماً (تغيير المسار)
    وهذا شائع جداً؛ كل دالة تسلّمك كائناً من نوع جديد، فتستدعي دوال هذا النوع الجديد:

    Java

    int len = student.getName()      // ترجع كائن String
                 .toUpperCase()  // دالة تابعة لـ String وترجع String
                 .length();      // دالة تابعة لـ String وترجع int (هنا تتوقف السلسلة)

2. بخصوص مثالك الثاني: "الأولى static والباقي مش static"

تحليلك هنا صحيح 100%، والسبب المنطقي خلفه هو:

  1. في البداية لا يوجد لدينا كائن جاهز في الذاكرة، فنستدعي دالة static باسم الكلاس مباشرة (مثل Student.builder() أو Optional.of("Ali")).
  1. وظيفة هذه الدالة الـ static أنها تخلق وتُرجع كائناً حقيقياً (Instance).
  1. بمجرد أن أصبح بين يديك كائن حقيقي، فإن أي دالة تأتي بعده تكون غير ستاتيك (Instance Method) لأنها تُنفَّذ على هذا الكائن المُرجَع.

(ملاحظة جانبية: لو حدث ووضعت دالة static في منتصف السلسلة، فالجافا تسمح بذلك تقنياً بناءً على نوع الكائن المُرجَع، لكنه يُعد أسلوباً سيئاً في الكتابة).

3. متى يُمنع وضع نقطة (.) وتنكسر السلسلة؟ (حالات الفشل)

تتوقف السلسلة ولا يمكنك إضافة أي دالة بعدها في 3 حالات:

  1. إذا كانت الدالة تُرجع void: لأنها لا تُرجع شيئاً أصلاً لكي تضع بعده نقطة (مثل System.out.println("Hi").length() -> خطأ فوري).
  1. إذا أرجعت نوعاً بدائياً (Primitive Type): مثل int، double، boolean، char. هذه الأنواع ليست كائنات في جافا ولا تحتوي على دوال، لذلك بمجرد أن تُرجع دالة رقماً مثل .length() أو .age() تنتهي السلسلة فوراً.
  1. إذا أرجعت null أثناء التشغيل: الكود سيُكتب بدون أخطاء برمجية (Compile-time)، لكن بمجرد أن تُرجع إحدى الدوال null وتحاول الدالة التي بعدها وضع نقطة عليها، سينهار البرنامج بخطأ NullPointerException (وهذا هو السبب الذي جعلنا نستخدم Optional في مثالك السابق لتجنب هذا الانهيار).

الخلاصة كقاعدة عامة تحفظها دائماً:

لكي تكتب a().b().c() في جافا:
  • نوع الإرجاع لدالة a() يجب أن يكون كلاس (Class / Interface) مُعرَّف بداخله دالة اسمها b().
  • نوع الإرجاع لدالة b() يجب أن يكون كلاس (Class / Interface) مُعرَّف بداخله دالة اسمها c().
