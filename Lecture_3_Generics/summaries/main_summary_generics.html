المحور الأول: الفلسفة والمشكلة التي حلتها التعميمات (Generics)

التعميمات (Generics) هي ميزة أُضيفت في إصدار جافا الخامس، وتسمح لك بكتابة كلاسات، واجهات (Interfaces)، ودوال (Methods) تعمل مع أنواع بيانات مختلفة دون الحاجة لتكرار الكود، مع الحفاظ الكامل على فحص الأخطاء أثناء كتابة الكود (Compile-time Type Safety).

كيف كنا نكتب الكود قبل التعميمات؟

قبل وجود التعميمات، إذا أراد مبرمج إنشاء قائمة (ArrayList) تخزن أي نوع من البيانات، كانت الجافا تخزن العناصر بداخلها على أنها من نوع Object (الأب الأعلى لكل الكلاسات). هذا الأسلوب كان يسبب كارثتين:

  • غياب الحماية أثناء الكتابة: كان بإمكانك وضع نص (String) ورقم (Integer) وكائن طالب (Student) في نفس القائمة دون أن يعترض المترجم (Compiler)، لأن الجميع يرث من Object.
  • انهيار السيرفر أثناء التشغيل (ClassCastException): عند استخراج البيانات من القائمة، كنت مجبراً على عمل تحويل يدوي (Explicit Casting)، وإذا أخطأت في نوع العنصر، ينهار التطبيق فجأة في وقت التشغيل (Runtime).

Java

// الطريقة القديمة الخطيرة (بدون Generics)
List list = new ArrayList();
list.add("Mohanad");
list.add(23); // المترجم يسمح بإضافة رقم مع النص دون أي اعتراض!

// الكارثة تحدث هنا عند التشغيل: محاولة تحويل الرقم إلى نص ترمي ClassCastException
String name = (String) list.get(1);

كيف أنقذت التعميمات المبرمجين؟

عندما تكتب List<String>، فأنت تُمرر النوع String كـ "معامل نوع" (Type Parameter) إلى الكلاس List. وبذلك تكسب ثلاث مزايا جوهرية:

  • حماية صارمة وقت الكتابة (Compile-time Safety): إذا حاولت إضافة رقم إلى List<String>، يظهر خطأ أحمر فوراً قبل تشغيل البرنامج.
  • إلغاء التحويل اليدوي (No Explicit Casting): المترجم يعرف مسبقاً أن كل ما يخرج من الصندوق هو String، فيقوم بالتحويل نيابةً عنك في الخلفية.
  • إعادة استخدام البنية البرمجية (Code Reusability): بدلاً من كتابة كلاس StudentRepository وآخر CourseRepository وثالث TeacherRepository بنفس الدوال، تكتب كلاساً معمماً واحداً JpaRepository<T, ID> يخدم النظام كله.

اصطلاحات التسمية المتفق عليها بين المبرمجين

يمكنك كتابة أي اسم داخل الأقواس المثلثة <...>، لكن المجتمع البرمجي وإطار عمل Spring يلتزمون بحروف موحدة لتسهيل قراءة الكود:

الحرفالكلمة الإنجليزيةدلالته واستخدامه الشائع
الحرف Tاختصار Typeيمثل أي نوع كائن عام (مثل ApiResponse<T>).
الحرف Eاختصار Elementيُستخدم في هياكل البيانات والمجموعات (مثل List<E> و Set<E>).
الحرف Kاختصار Keyيمثل المفتاح في الخرائط (مثل Map<K, V>).
الحرف Vاختصار Valueيمثل القيمة المقابلة للمفتاح (مثل Map<K, V>).
الحرف Rاختصار Returnيمثل نوع النتيجة العائدة في البرمجة الوظيفية (مثل Function<T, R>).
الرمز IDاختصار Identifierشائع جداً في Spring Data لتمثيل نوع المفتاح الأساسي (مثل Long أو UUID).

المحور الثاني: بناء الكلاسات والواجهات والدوال المعممة

أولاً: الكلاس المعمم (Generic Class)

لجعل الكلاس معمماً، نضع معامل النوع <T> بعد اسم الكلاس مباشرة. عندها يصبح T متاحاً كنوع بيانات لأي متغير أو دالة داخل الكلاس.

Java

// تعريف كلاس معمم يعمل كصندوق لأي نوع بيانات
public class DataBox<T>{
    private T content;

    public void put(T content){
        this.content = content;
    }

    public T get(){
        return this.content;
    }
}

// طريقة الاستخدام: نحدد النوع الفعلي عند إنشاء الكائن
DataBox<String> textBox = new DataBox<>(); // استخدام رمز الماسة Diamond Operator
textBox.put("Spring Boot");
String value = textBox.get(); // لا حاجة لأي Casting

ثانياً: تعدد المعاملات (Multiple Type Parameters)

يمكن للكلاس استقبال أكثر من نوع في نفس الوقت عبر الفصل بينها بفاصلة، وهو أسلوب أساسي في تصميم استجابات الـ API أو هياكل البيانات المزدوجة.

Java

public class Pair<K, V>{
    private final K key;
    private final V value;

    public Pair(K key, V value){
        this.key = key;
        this.value = value;
    }

    public K getKey(){ return key; }
    public V getValue(){ return value; }
}

// مثال الاستخدام
Pair<Long, String> userRole = new Pair<>(101L, "ROLE_ADMIN");

ثالثاً: الواجهة المعممة (Generic Interface) وأساسيات Spring Data

الواجهات المعممة هي العمود الفقري لطبقة قواعد البيانات في Spring Boot. عندما ترث واجهتك من JpaRepository<User, Long>، فأنت تطبق هذا المفهوم تماماً.

Java

// تعريف عقد عام لأي مستودع بيانات في النظام
public interface BaseRepository<T, ID>{
    T save(T entity);
    Optional<T> findById(ID id);
    void deleteById(ID id);
}

// كلاس يطبق الواجهة لكيان محدد (User) ومفتاح من نوع (Long)
public class UserRepositoryImpl implements BaseRepository<User, Long>{
    @Override
    public User save(User entity){ /* كود الحفظ */ return entity; }

    @Override
    public Optional<User> findById(Long id){ /* كود البحث */ return Optional.empty(); }

    @Override
    public void deleteById(Long id){ /* كود الحذف */ }
}

رابعاً: الدالة المعممة (Generic Method)

أحياناً يكون الكلاس نفسه عادياً (غير معمم)، لكنك تحتاج إلى دالة واحدة بداخله تقبل أنواعاً مختلفة. هنا نضع <T> قبل نوع الإرجاع (Return Type) الخاص بالدالة.

  • ملاحظة مهمة: الدوال الثابتة (static) داخل الكلاس المعمم لا تستطيع رؤية الـ <T> الخاص بالكلاس؛ لأن static يتبع الكلاس قبل إنشاء أي كائن، لذلك يجب أن تُعرّف الدالة الـ static معاملها <T> الخاص بها.

Java

public class JsonUtils{

    // دالة ثابتة معممة: <T> تُكتب قبل نوع الإرجاع T
    public static <T> T printAndReturn(T item){
        System.out.println("Processing item: " + item);
        return item;
    }
}

// المترجم يستنتج النوع تلقائياً (Type Inference) دون الحاجة لكتابته
String s = JsonUtils.printAndReturn("Hello");
Integer num = JsonUtils.printAndReturn(500);

المحور الثالث: تقييد الأنواع (Bounded Type Parameters)

عندما تكتب <T> بدون قيود، فإن المترجم يعامل T على أنه Object؛ وبالتالي لا يمكنك استدعاء سوى دوال Object عليه (مثل toString و equals).
ولكن ماذا لو كنت تبني نظاماً وتريد السماح فقط للكائنات التي ترث من BaseEntity لكي تتمكن من استدعاء entity.getId() بأمان؟ هنا نستخدم الكلمة المفتاحية extends.

تقييد النوع بكلاس أو واجهة واحدة

نستخدم extends دائماً سواء كان القيد كلاساً أو واجهة (Interface):

Java

// الكلاس الأب المشترك لكل جداول قاعدة البيانات
public abstract class BaseEntity{
    private Long id;
    public Long getId(){ return id; }
}

// الآن T مقيد: يُسمح فقط بـ BaseEntity أو أي كلاس يرث منه
public class EntityAuditor<T extends BaseEntity>{

    public void logEntityId(T entity){
        // المترجم يسمح باستدعاء getId() لأنه متأكد أن T يرث من BaseEntity
        System.out.println("Auditing entity with ID: " + entity.getId());
    }
}

تعدد القيود (Multiple Bounds)

يمكنك إجبار النوع T على تحقيق أكثر من شرط في آنٍ واحد باستخدام علامة &، بشرط الالتزام بقاعدة صارمة: إذا كان هناك كلاس ضمن القيود، يجب أن يُكتب أولاً قبل الواجهات (Interfaces).

Java

// صحيح: الكلاس BaseEntity أولاً، ثم الواجهات
public class CacheManager<T extends BaseEntity & Serializable & Comparable<T>>{
    // ...
}

// خطأ برمجي: لا يجوز وضع الواجهة قبل الكلاس
// public class CacheManager<T extends Serializable & BaseEntity> {}

المحور الرابع: البدل والمرونة (Wildcards) ومبدأ PECS

هذا المحور هو الفارق الحقيقي بين المبرمج المبتدئ والمحترف في الجافا.

لغز الوراثة في القوائم (Invariance)

نعلم أن كلاس Dog يرث من Animal. ولكن في الجافا: قائمة الكلاب List<Dog> ليست ابنة لقائمة الحيوانات List<Animal>!
لماذا منعت الجافا ذلك؟ تخيل لو سمحت الجافا بتمرير List<Dog> إلى دالة تستقبل List<Animal>؛ عندها ستتمكن الدالة من إضافة كائن Cat داخل القائمة باعتبارها قائمة حيوانات، فتفسد قائمة الكلاب وتنهار عند القراءة!

لحل هذه المشكلة وتوفير المرونة في مدخلات الدوال، ابتكرت الجافا علامة البدل ? (Wildcard) التي تعني "نوع غير معروف".

أنواع البدل الثلاثة

  • البدل غير المقيد (<?>): يقبل قائمة من أي نوع على الإطلاق. يُستخدم عندما تعتمد الدالة فقط على دوال Object أو حجم القائمة دون الاهتمام بنوع العناصر.
  • البدل المقيد بحد أعلى (<? extends T>): يقبل T أو أي كلاس يرث منه (أبناؤه).
  • البدل المقيد بحد أدنى (<? super T>): يقبل T أو أي كلاس يعلوه في الوراثة (آباؤه وصولاً إلى Object).

القاعدة الذهبية: مبدأ PECS

اختصار لعبارة: Producer Extends, Consumer Super (المُنتِج يأخذ extends، والمُستهلك يأخذ super).

  • متى تستخدم <? extends T> (المُنتِج - Producer)؟
    عندما تكون القائمة تُنتج لك بيانات لتقرأها فقط. أنت متأكد أن كل عنصر يخرج منها هو على الأقل من نوع T (مثلاً Number)، لكن يُمنع عليك الإضافة إليها لأنك لا تعرف هل القائمة الأصلية List<Integer> أم List<Double>.
  • متى تستخدم <? super T> (المُستهلك - Consumer)؟
    عندما تريد إضافة (استهلاك) عناصر من نوع T إلى القائمة. أنت متأكد أن القائمة تستوعب T (سواء كانت List<Integer> أو List<Number> أو List<Object>)، لكن عند القراءة منها لن تحصل إلا على Object.

Java

public class WildcardDemo{

    // Producer: نقرأ الأرقام من القائمة ونجمعها -> نستخدم extends
    public static double sumNumbers(List<? extends Number> numbers){
        double total = 0.0;
        for (Number n : numbers) { // القراءة آمنة تماماً
            total += n.doubleValue();
        }
        // numbers.add(10); // ممنوع! خطأ ترجمة لأننا لا نعرف النوع الدقيق للقائمة
        return total;
    }

    // Consumer: نضيف أرقاماً صحيحة إلى القائمة -> نستخدم super
    public static void addDefaultIds(List<? super Integer> list){
        list.add(1); // الإضافة آمنة لأن القائمة إما Integer أو Number أو Object
        list.add(2);
    }
}

المحور الخامس: ما يحدث خلف الكواليس — محو الأنواع (Type Erasure)

لكي تحافظ الجافا على التوافق مع الإصدارات القديمة جداً، قرر مصممو اللغة أن التعميمات (Generics) تكون موجودة فقط أثناء كتابة الكود وترجمته (Compile-time)، ثم يتم مسحها بالكامل قبل تشغيل البرنامج (Runtime). هذه العملية تُسمى محو الأنواع (Type Erasure).

كيف يتعامل المترجم مع التعميمات؟

عند ترجمة الكود إلى Bytecode، يقوم المترجم بالآتي:

  • يستبدل كل معامل نوع غير مقيد <T> بكلاس Object.
  • يستبدل كل معامل نوع مقيد <T BaseEntity extends> بالحد الأعلى له وهو BaseEntity.
  • يقوم بحقن عمليات التحويل (Cast) تلقائياً في الأماكن التي تستخرج فيها البيانات.

بمعنى آخر، في الذاكرة أثناء التشغيل (Runtime)، لا يوجد فرق بين List<String> و List<Integer>؛ كلاهما يصبح مجرد List خام!

القيود الممنوعة بسبب محو الأنواع

بسبب اختفاء نوع T في وقت التشغيل، تفرض الجافا قيوداً مهمة يجب أن تفهم سببها:

  • منع إنشاء كائن مباشر (new T()): لأن المترجم لا يعرف أي Constructor يستدعي في وقت التشغيل. (الحل في الـ Backend هو تمرير Class<T> clazz واستخدام Reflection).
  • منع إنشاء مصفوفة معممة (new T[]): لأن المصفوفات في الجافا تحتفظ بنوعها الحقيقي في وقت التشغيل بعكس التعميمات.
  • منع استخدام الأنواع البدائية (Primitives): لا يمكنك كتابة List<int> لأن int لا يرث من Object؛ يجب استخدام الكلاسات المغلفة مثل List<Integer>.
  • منع الفحص باستخدام instanceof: لا يمكنك كتابة if (obj instanceof List<String>) لأن معلومة <String> قد مُحيت أصلاً أثناء التشغيل.
  • منع استخدام T في الحقول الثابتة (static): لأن المتغير الـ static مشترك بين كل الكائنات؛ فلو أنشأت Box<String> و Box<Integer>، لن يعرف المتغير الـ static أي نوع يتبع.

كيف يتغلب Spring على محو الأنواع؟ (ParameterizedTypeReference)

في مشاريع الـ Backend، عندما تستخدم RestTemplate أو WebClient لاستدعاء خدمة خارجية تُرجع قائمة مستخدمين List<UserDto>، لا يمكنك كتابة List<UserDto>.class بسبب محو الأنواع.

لحل هذه المعضلة، ابتكر فريق Spring كلاساً عبقرياً يُسمى ParameterizedTypeReference<T> يعتمد على حيلة تُعرف بـ Super Type Tokens:

Java

// استخدام الأقواس المتعرجة {} في النهاية ينشئ كلاساً ابناً مجهولاً (Anonymous Subclass)
// الجافا تحتفظ بمعلومات الوراثة للكلاسات الأبناء في الـ Bytecode حتى في وقت التشغيل!
ResponseEntity<List<UserDto>> response = restTemplate.exchange(
    "https://api.example.com/users",
    HttpMethod.GET,
    null,
    new ParameterizedTypeReference<List<UserDto>>() {}
);

List<UserDto> users = response.getBody();

يستغل Spring هنا حقيقة أن محو الأنواع يمسح نوع الكائن نفسه، لكنه لا يمسح توقيع الكلاس الأب الذي يرث منه كلاس فرعي؛ فيقوم Spring بقراءة النوع List<UserDto> باستخدام الـ Reflection عبر دالة getGenericSuperclass() ويمرره لمكتبة Jackson لتحويل الـ JSON بدقة متناهية.

المحور السادس: تطبيقات احترافية في Spring Boot و Backend

إتقان التعميمات ينقلك مباشرة من كتابة كود مكرر إلى بناء معمارية نظيفة (Clean Architecture) قابلة للتوسع في مشاريع Spring Boot.

أولاً: تغليف ردود السيرفر الموحدة (Unified API Response)

في أي نظام Backend احترافي، يجب أن يخرج كل رد من الـ REST API بنفس الهيكل الثابت للواجهة الأمامية (Frontend)، مع اختلاف نوع البيانات (data) من شاشة لأخرى (مرة يكون UserDto، ومرة List<CourseDto>، ومرة String). التعميمات هي الحل المثالي هنا:

Java

public class ApiResponse<T>{
    private boolean success;
    private String message;
    private T data;
    private LocalDateTime timestamp;

    public ApiResponse(boolean success, String message, T data){
        this.success = success;
        this.message = message;
        this.data = data;
        this.timestamp = LocalDateTime.now();
    }

    // دوال مساعدة سريعة لإنشاء الردود
    public static <T> ApiResponse<T> ok(T data, String message){
        return new ApiResponse<>(true, message, data);
    }

    public static <T> ApiResponse<T> error(String message){
        return new ApiResponse<>(false, message, null);
    }

    // Getters...
}

وعند استخدامه في أي RestController يصبح الكود نظيفاً ومقروءاً للغاية:

Java

@GetMapping("/{id}")
public ResponseEntity<ApiResponse<StudentDto>> getStudent(@PathVariable Long id) {
    StudentDto dto = studentService.findById(id);
    return ResponseEntity.ok(ApiResponse.ok(dto, "Student retrieved successfully"));
}

ثانياً: بناء خدمة أساسية موحدة (Generic Base Service)

بدلاً من تكرار دوال الحفظ والبحث والحذف في كل Service (مثل StudentService و DepartmentService و TeacherService)، يمكنك بناء كلاس مجرد معمم يجمع العمليات المشتركة ويربطها مع JpaRepository:

Java

public abstract class BaseService<T extends BaseEntity, ID>{

    // نجبر كل كلاس ابن على تزويدنا بالـ Repository الخاص به
    protected abstract JpaRepository<T, ID> getRepository();

    public T save(T entity){
        return getRepository().save(entity);
    }

    public T findByIdOrThrow(ID id){
        return getRepository().findById(id)
            .orElseThrow(() -> new ResourceNotFoundException("Record not found with id: " + id));
    }

    public List<T> findAll(){
        return getRepository().findAll();
    }

    public void deleteById(ID id){
        T entity = findByIdOrThrow(id);
        getRepository().delete(entity);
    }
}

الآن، عندما تنشئ خدمة جديدة مثل DepartmentService، ترث كل هذه الوظائف الجاهزة بسطور معدودة، وتتفرغ فقط لكتابة منطق العمل الخاص بالأقسام:

Java

@Service
public class DepartmentService extends BaseService<Department, Long>{

    private final DepartmentRepository departmentRepository;

    public DepartmentService(DepartmentRepository departmentRepository){
        this.departmentRepository = departmentRepository;
    }

    @Override
    protected JpaRepository<Department, Long> getRepository(){
        return this.departmentRepository;
    }

    // هنا تكتب فقط الدوال الخاصة بالأقسام مثل البحث برمز القسم
}

هل تود أن نطبق نفس هذا الأسلوب المعمم لبناء BaseController موحد في Spring Boot يختصر نقاط النهاية (Endpoints) الأساسية للـ CRUD؟
