أولاً: الواجهات في الجافا (Interfaces)

الـ Interface عبارة عن عقد برمجي (Contract) يحدد السلوكيات والمهارات التي يجب على الكلاسات الالتزام بتنفيذها. تكون الواجهة عقداً عاماً متاحاً لجميع الـ Packages في المشروع بشرط تعريفها بكلمة public هكذا: public interface MyContract، أما إذا كُتبت interface MyContract بدون public فتكون مرئية داخل نفس الـ Package فقط (Package-Private).

المتغيرات داخل الواجهة (Variables)

  • أي متغير يُعرّف داخل الـ Interface يجعله المترجم تلقائياً (By Default) عبارة عن public static final حتى لو لم تكتب هذه الكلمات.
  • يجب إعطاؤه قيمة ابتدائية لحظة تعريفه (Must have an initial value) بسبب كلمة final؛ لأنه ثابت مشترك على مستوى الواجهة ولا يمثل حالة متغيرة لكائن.
  • يُمنع وضع معدلات وصول private أو protected للمتغيرات داخل الواجهة.

معدلات الوصول للدوال (Access Modifiers)

  • المسموح فقط للدوال داخل الواجهة هما: public و private.
  • الممنوع نهائياً داخل الواجهة هما: protected و default (Package-Private).
  • تنبيه مهم: إذا كتبت دالة في الـ Interface بدون كتابة public (مثل void login();)، فهي ليست Package-Private كما يحدث في الكلاسات العادية، بل يجعلها المترجم public تلقائياً.

أنواع الدوال الخمسة داخل الواجهة

  • الدوال المجردة (Abstract Methods): دوال بدون جسم (Body) وتنتهي بفاصلة منقوطة. يجب على الكلاس الابن (غير المجرد) عمل Override وتنفيذها جميعاً. يكون معدل وصولها public abstract تلقائياً، ويُمنع وضع private أو final أو static معها.
  • الدوال الافتراضية (Default Methods): أُضيفت منذ Java 8، ويجب أن تحتوي على Body عند إنشائها وتُسبق بكلمة default (وهنا كلمة default تعني أن لها تنفيذاً افتراضياً وليست معدل وصول، ومعدل وصولها يكون public تلقائياً). يمكن للكلاس الابن وراثتها كما هي أو عمل Override لإعادة تعريفها.
  • الدوال الثابتة (Static Methods): أُضيفت منذ Java 8، ويجب أن تحتوي على Body. هي دوال ملك للواجهة الأب فقط (Interface) ولا تُورّث للأبناء ولا يمكن عمل Override لها. عند استدعائها يجب مناداتها باسم الواجهة فقط (مثل MyInterface.helper()) وليس عن طريق كائن من الابن.
  • الدوال الخاصة العادية (Private Instance Methods): أُضيفت منذ Java 9، ويجب أن تحتوي على Body وتُسبق بكلمة private (مثل private void logTransaction()). وظيفتها تقليل تكرار الكود بين دوال الـ default داخل نفس الواجهة؛ لأن دوال الـ default دوال تابعة للكائن وتحتاج أحياناً لمناداة دوال مساعدة غير static دون كشفها للخارج أو السماح بعمل Override لها.
  • الدوال الخاصة الثابتة (Private Static Methods): أُضيفت منذ Java 9، ويجب أن تحتوي على Body. هي دوال ملك للواجهة الأب فقط ولا يمكن عمل Override لها، ولا يمكن استدعاؤها خارج الواجهة سواء باسم الواجهة أو عن طريق كائن (Object). وظيفتها تقليل تكرار الكود بين دوال الـ static داخل الواجهة (ويمكن مناداتها أيضاً داخل دوال الـ default والـ private العادية في نفس الواجهة).

قواعد وتنبيهات إضافية في الواجهات

  • لماذا يُمنع وضع private مع دوال abstract و default؟ لأن دالة abstract يجب أن يتم تنفيذها (Implementation) في الكلاس الابن، ودالة default وظيفتها إتاحة عمل Override لها في الكلاس الابن؛ فلو كانتا private لما استطاع الابن رؤيتهما أو الوصول إليهما لتنفيذهما أو تعديلهما.
  • عدم وجود دوال بناء (Constructors): لا يمكن إنشاء كائن مباشر من الـ Interface بكلمة new، كما أنها لا تمتلك Constructor لأنها لا تحتوي على متغيرات حالة (Instance Variables) لتهيئتها.
  • حل تعارض دوال الـ default (Diamond Problem): إذا طبق كلاس واجهتين (A و B) وكلتاهما تحتويان على دالة default بنفس الاسم والمدخلات، سيعترض المترجم (Compile Error) ويجبر الكلاس الابن على عمل Override للدالة لحسم التعارض بنفسه (ويمكنه بداخلها اختيار تنفيذ إحداهما عبر A.super.methodName()).

ثانياً: الكلاس المجرد (Abstract Class)

الـ Abstract Class هو عبارة عن الكلاس القالب (Template) الذي يمثل الأصل المشترك لمجموعة من الكلاسات التي ترث منه عبر extends. لا يمكن إنشاء كائن (Object) منه مباشرة بكلمة new، بل يجب أن يرثه كلاس ابن ليُكمل بناءه.

المتغيرات ودوال البناء داخل الكلاس المجرد

  • المتغيرات (Variables): يمكنك كتابة شتى أنواع المتغيرات بداخله بدون قيود، سواء متغيرات عادية متغيرة القيمة (Instance Variables)، أو static، أو final، أو static final، وبجميع معدلات الوصول الأربعة (public, protected, default, private).
  • دوال البناء (Constructors): على عكس الواجهة، يمتلك الكلاس المجرد Constructor؛ ورغم أنك لا تستطيع إنشاء كائن منه مباشرة، إلا أن الـ Constructor الخاص به يُستدعى تلقائياً عبر super() عند إنشاء كائن من الكلاس الابن لتهيئة المتغيرات المشتركة في الأب.

أنواع الدوال الأربعة داخل الكلاس المجرد

  • الدوال المجردة (Abstract Methods): دوال بدون Body وتُسبق بكلمة abstract، وتُجبر الكلاس الابن على عمل Override وتنفيذها. يُسمح معها بمعدلات الوصول public أو protected أو default (Package-Private)، ويُمنع تماماً وضع private أو final أو static معها.
  • الدوال العادية مكتملة التنفيذ (Regular / Concrete Methods): دوال عادية لها Body يرثها الأبناء كما هي ويمكنهم عمل Override لها.
  • الدوال النهائية (Final Methods): دوال لها Body وتُسبق بكلمة final. يرثها الأبناء ويستخدمونها كما هي، ولكن يُمنع منعاً باتاً عمل Override لها لحماية المنطق الأساسي من التغيير.
  • الدوال الثابتة (Static Methods): دوال لها Body وتُسبق بكلمة static، وهي تابعة للكلاس الأب وتُستدعى باسمه.
  • الممنوعات في أنواع الدوال: يُمنع استخدام كلمة default كنوع دالة كما في الـ Interface؛ لأن الدوال مكتملة التنفيذ في الكلاس المجرد تُكتب كدوال عادية مباشرة بدون كلمة default.

السر المعماري لمعدلات الوصول داخل الكلاس المجرد

  • أهمية معدل الوصول protected: تُعد كلمة protected أهم معدل وصول داخل الـ Abstract Class لسبب معماري جوهري؛ فلو جعلت الدالة أو المتغير public، سيتمكن أي كلاس غريب في المشروع (حتى لو لم يرث من الكلاس المجرد) من الوصول إليها واستدعائها (خاصة في حالة static أو عند التعامل مع الكائن). أما عندما تجعلها protected، فأنت تسمح للأبناء فقط (حتى لو كانوا في Packages أخرى خارجية) بالوصول إليها واستخدامها، بينما تحميها وتخفيها عن باقي الكلاسات الغريبة في المشروع — وهذا هو أساس نمط التصميم الشهير Template Method Pattern الذي تعتمد عليه كلاسات Spring Security بكثرة.
  • استخدام معدل الوصول default (Package-Private): أي كتابة الدالة أو المتغير بدون معدل وصول. يستخدمه مصممو المكتبات عن قصد عندما يريدون السماح بالوراثة والوصول للكلاسات الموجودة داخل نفس الـ Package فقط ومنع أي Package خارجية من وراثة هذا الكلاس أو إكماله.

ثالثاً: الفرق الجوهري وقواعد الوراثة (Abstract vs Interface)

يمكن تلخيص الفلسفة الهندسية بينهما في قاعدتين أساسيتين: الكلاس المجرد يعبر عن هوية الشيء (Is-A)، بينما الواجهة تعبر عن قدرة أو سلوك إضافي (Can-Do).

الكلاس المجرد (Abstract Class) = الهوية والأصل المشترك (Is-A)

  • الاستخدام: تستخدمه عندما تكون لديك مجموعة من الكائنات التي تنتمي لنفس العائلة ولها نفس الجوهر، وتريد مشاركة كود وحالة (State) مشتركة بينها لتجنب التكرار.
  • التركيز على الحالة (State): السبب الرئيسي لوجود متغيرات عادية (غير final) فيه هو أن الكائنات التي ترث منه تحتاج للاحتفاظ ببيانات تتغير مع الوقت، مثل speed أو batteryLevel.
  • الأصل الواحد (extends): في الواقع والبرمجة، الكائن له أصل واحد فقط ينتمي إليه؛ فالسيارة هي مركبة (Car extends Vehicle)، ولا يمكن أن تكون مركبة وحيواناً في نفس الوقت.

الواجهة (Interface) = القدرات والمهارات (Can-Do)

  • الاستخدام: تستخدمها لتحديد سلوكيات أو قدرات يمكن إضافتها لأي كلاس، حتى لو كانت هذه الكلاسات لا تربطها أي صلة قرابة ببعضها البعض.
  • التركيز على السلوك (Behavior): لا يهمها كيف يخزن الكلاس بياناته، بل يهمها فقط أن الكلاس يلتزم بتنفيذ أوامر معينة؛ لذلك لا تسمح بمتغيرات حالة متغيرة (Non-final) لأن الواجهة لا تملك حالة خاصة بها.
  • تعدد القدرات (implements): الكائن الواحد يمكن أن يمتلك عدة مهارات في نفس الوقت؛ فمثلاً الطائرة (Airplane) هي في الأصل مركبة (extends Vehicle)، لكنها تمتلك قدرات إضافية فتطبق واجهات مثل Flyable (قابل للطيران) و Insured (مؤمّن عليه).

قواعد الوراثة والتطبيق الصارمة (extends و implements)

  • الوراثة (extends): تكون بين نفس نوع الملف فقط. في حالة الكلاسات يُسمح بعمل extends لكلاس واحد فقط (Single Inheritance) سواء كان عادياً أو مجرداً، أما في حالة الـ Interfaces فتستطيع الواجهة عمل extends لأكثر من واجهة في نفس الوقت (interface C extends A, B).
  • التطبيق (implements): يكون من الكلاس (العادي أو المجرد) للواجهات (Interfaces) فقط، ويمكن للكلاس تطبيق أكثر من واجهة في نفس الوقت (class X implements A, B).
  • الحالة الوحيدة الممنوعة (Compile Error): أن تتطابق الدالتان في الواجهتين في الاسم والمدخلات (Method Signature)، وتختلفا في نوع الإرجاع (Return Type)؛ مثل وجود int test() في الواجهة الأولى و String test() في الواجهة الثانية، فهنا يستحيل على الكلاس تطبيق الواجهتين معاً لأن المترجم لا يستطيع بناء دالتين بنفس الاسم والمدخلات داخل كلاس واحد.

رابعاً: لماذا ابتكروا Interface رغم أن Abstract Class يمتلك كل خصائصه؟

  • كسر قيد الوراثة الأحادية (Single Inheritance): في لغة جافا، يُمنع الكلاس من عمل extends لأكثر من كلاس واحد لتجنب تضارب الحالة (State Diamond Problem). لو لم يوجد Interface، لما استطاع كلاس واحد اكتساب قدرات متعددة من مصادر مختلفة (مثلاً كلاس User يرث من BaseEntity وفي نفس الوقت يطبق Serializable و Comparable وواجهة UserDetails في Spring Security).
  • العزل التام بين العقد والتنفيذ (Decoupling): الـ Interface يمثل عقداً نقياً خالياً من أي حالة داخلية (State)، وهذا هو حجر الأساس في Spring Framework ومبدأ حقن التبعيات (Dependency Injection)؛ حيث يتعامل الـ Controller مع واجهة UserService دون معرفة الكلاس الحقيقي الذي ينفذها، مما يسهل تبديل التنفيذ أو عمل اختبار وهمي (Mocking).
  • دعم البرمجة الوظيفية (Lambdas): تعبيرات الـ Lambda في Java 8 وما بعدها صُممت للعمل حصرياً مع الواجهات الوظيفية (Functional Interfaces) ولا يمكن استخدامها نهائياً مع الـ Abstract Class.

خامساً: كيف نضع عدة نقاط متتالية عند استدعاء الدوال (Method Chaining)؟

عندما ترى كوداً يحتوي على عدة نقاط متتالية مثل System.out.println(...) أو إعدادات Spring Security مثل http.cors(...).csrf(...)، فهناك آليتان برمجيتان تقفان خلف هذا الشكل:

  • الحالة الأولى — الوصول المتسلسل للكائنات (Object Traversal): مثل جملة System.out.println("Hello"). هنا System هو اسم كلاس، وبداخله متغير static اسمه out ونوعه PrintStream، وداخل كلاس PrintStream توجد دالة println(). النقطة الأولى تدخلك إلى الكائن out، والنقطة الثانية تستدعي دالة من داخل ذلك الكائن.
  • الحالة الثانية — تسلسل استدعاء الدوال (Method Chaining / Fluent API): مثل sb.append("A").append("B") أو إعدادات Spring Security. السر الهندسي لكتابتها في كلاسك هو سطر واحد فقط: تجعل نوع الإرجاع (Return Type) للدالة هو نفس نوع الكلاس الحالي، وتضع في نهاية الدالة جملة return this; لكي تُرجع نفس الكائن وتسمح بوضع نقطة مباشرة بعد القوس لاستدعاء الدالة التالية.

Java

public class RequestBuilder{
    private String url;
    private String method;

    public RequestBuilder setUrl(String url){
        this.url = url;
        return this; // إرجاع نفس الكائن الحالي لتمكين النقطة التالية
    }

    public RequestBuilder setMethod(String method){
        this.method = method;
        return this; // إرجاع نفس الكائن الحالي
    }

    public void send(){
        System.out.println("Sending " + method + " to " + url);
    }
}
